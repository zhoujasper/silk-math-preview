# TikZ 性能与正确性记录（0.2.1）

2026-09-07，本机 macOS、VS Code 自带 Node 24.18.1。只运行独立 Node / WASM Worker，
未打开浏览器或 Extension Host。以下是指定图形的实测，不能作为任意 TikZ 的实时承诺。

## 同环境前后对照：外部宏连续编辑

同一个 `8×4 cm`、30 samples、带网格的抛物线，每帧改变外部 `\def\offset`，
21 次请求。旧 Worker 已修复 pgfplots 1.18.3，但仍使用合并的宏包/定义检查点；
最终 Worker 分开缓存两层并共享未变化的页。两次运行连续执行，没有并行跑性能任务。

| 指标 | 优化前 | 0.2.1 最终实现 |
|---|---:|---:|
| 首次渲染（含 Worker 启动） | 475.79 ms | 481.26 ms |
| 连续编辑 p50 | 319.53 ms | 103.01 ms |
| 连续编辑 p95 | 324.68 ms | 105.88 ms |
| 21 次请求累计 CPU | 7202.01 ms | 2798.93 ms |
| 测试进程峰值 RSS | 297.81 MiB | 283.34 MiB |
| 空闲 250 ms 的 CPU | 0.55 ms | 1.39 ms |

热更新中位耗时下降约 68%，累计 CPU 下降约 61%。首次初始化没有同等改善。
依据：`.tmp-tikz-smoke/definitions-before.json`、`definitions-after.json`。

## 常见及复杂图形

真实 Worker 通过 96 次正确性/恢复请求：31 种绘图库图形、8 个兼容/设置场景、
3 种额外环境，以及 16 组原生宏定义对照、错误、资源限制、超时和空闲恢复。
覆盖分组图、填充、统计、日期、极坐标、三元图、Smith 图、曲面、参数曲线、向量场、
树、矩阵、交点、分层、电路、逻辑门、曲线文字、渐变、纹理、裁剪和透明度。
原生定义与显式展开后的 SVG 相同；错误输出、缺字和缺失图形定义不能当成成功。
最终正式安装包提取的 Worker 再次通过全部 96 次请求；36 张保存的实际 SVG 均由
默认独立图像读取器成功栅格化。

压力脚本每种图形做 6 次真实源码修改，另外测试 30 请求突发（28 个中间请求丢弃）、
30 次多公式标签连续编辑及空闲重启，共 109 个请求。图形均成功，109 请求中实际计算
81 次，其余 28 次被合并。最终长测有明显运行环境波动，不把它与前一轮直接当作速度提升比较。

| 真实编辑场景 | 早期平稳轮 p50 | 最终长测 p50 / 最大热帧 |
|---|---:|---:|
| 单曲线 30 点 | 88 ms | 268 / 274 ms |
| 修改图形前的定义 | 300 ms（尚未拆分缓存） | 276 / 277 ms |
| 8 条曲线 × 80 点 | 1025 ms | 3225 / 3277 ms |
| 6 个子图 × 60 点 | 659 ms | 1717 / 2126 ms |
| 25×25 点三维曲面 | 2274 ms | 7270 / 7386 ms |
| 60 节点、100 条连线 | 416 ms | 1353 / 1359 ms |
| 8×8 数学矩阵 | 229 ms | 745 / 781 ms |
| 80 个分式标签 | 293 ms | 354 / 802 ms |

最终长测最后 30 帧标签恢复到每帧不超过 324 ms。宿主事件循环 10 ms 采样定时器
p95 间隔 12.10 ms、最大 25.20 ms；这说明测试宿主没有被同步 TeX 阻塞，**并非编辑器
屏幕刷新时延的测量**。停止采样后空闲 500 ms 的 CPU 时间为 0.49 ms。
依据：`stress-before.json`、`stress-final.json`。PGF 密集曲面 CPU 采样中约 99% 的
时间在原生 TeX 运算。复杂图仍可能需要数秒，不能宣称都能在 100 ms 内完成。

## 内存与 SVG 正确性

- WASM 工作内存固定 68.75 MiB；核心、宏包、定义三份逻辑快照在抛物线场景分别约
  10.38 / 14.75 / 14.75 MiB，共享相同页后实际快照缓冲约 18.88 MiB。
- 每层只保留当前一份，字体最多 16 项。输出缓冲合计最多 8 MiB；图形/前置源码、
  标签数、文件数、SVG 大小继续受限。默认关闭时不启动 TikZ Worker。
- 最终长测进程峰值 RSS 279.28 MiB；最后 30 帧标签的前/后十帧最小 RSS 为
  270.28 / 277.66 MiB。未观察到按累计请求保留图片的行为，但有限时长测试不能证明
  所有工作负载无泄漏。空闲回收后 RSS 182.11 MiB，重新请求确实新建 Worker。
- RSS 包括测试驱动和 Node，受 GC、系统调度与内存回收影响；**不是 VS Code 总内存，
  也不是渲染器的净增量**。不要把它描述成几 MB 的轻量组件。正式空闲回收仍为 60 秒，
  测试缩短该时限；Esc/关闭/15 秒超时也会回收 Worker。
- 80 分式标签的同一帧 SVG 从 978,101 B 降到 100,233 B（约减少 90%）；轮廓原坐标、
  路径小数位和绘图顺序保持不变。7 组复杂图用独立 librsvg 栅格化，逐像素完全一致。
- 25×25 曲面旧 SVG 深度 1165，标准图像读取器拒绝；压平纯颜色分组后深度 8，
  默认读取器正常生成图片。变换、裁剪、命名引用和组透明度保留，另有 1200 层分组回归。
- 曲线交点库仅对校验过的四个递归函数提前释放参数帧，保留算法、精度和顺序；
  圆与线交点不再触发旧引擎的 300 项参数栈上限。其余 TeX 容量限制仍然存在。

输入合并另有约 80 ms，下载、编辑器 IPC 和实际屏幕绘制不计入上述渲染时间。
`path fading`、LuaTeX、外部文件/gnuplot、任意 CTAN 包、CJK 字体仍有明确支持边界。

## 复现

```sh
npm run build
npm run validate:tikz
npm run stress:tikz -- dist/tikz-worker.js .tmp-tikz-smoke/stress.json --soak
node scripts/benchmark-tikz.mjs dist/tikz-worker.js .tmp-tikz-smoke/definitions.json --definitions
```

可把 Worker 路径换成旧包提取的路径作对照。正式测量使用 VS Code 自带 Node 24.18.1
而非默认 shell 的 Node 26。中间报告、SVG、像素对照和 CPU 采样留在被忽略的
`.tmp-tikz-smoke/`，未随插件打包。最后图形界面验收按用户要求留给用户。

# 历史记录：0.1.81

2026-09-07，本机 macOS、VS Code 自带 Node 24.18.1。相同脚本、相同运行时组件，
分别运行 0.1.79 安装包提取的旧 Worker 和当前 Worker。每个进程连续完成 21 次用户的
8×4 cm、30 samples、网格抛物线示例，每次改变常数项；第一帧单列，其余 20 帧统计。
未启动浏览器、编辑器窗口或 Extension Host。数字仅代表此机器和样例。

| 指标 | 0.1.79 | 0.1.81 |
|---|---:|---:|
| 首次渲染（含 Worker 启动） | 543.9 ms | 494.3 ms |
| 连续编辑 p50 | 389.7 ms | 103.8 ms |
| 连续编辑 p95 | 391.6 ms | 106.8 ms |
| 测试进程峰值 RSS | 447.7 MiB | 275.7 MiB |
| 21 次请求累计 CPU 时间 | 7688.0 ms | 2831.7 ms |
| 空闲 250 ms 的 CPU 时间 | 1.1 ms | 2.3 ms |

RSS 是独立测试进程（驱动与 Worker）的驻留内存，包含 Node 固定开销，**不是 VS Code
整体内存，也不是新增渲染器的净内存**。底层 TeX 工作内存固定 68.75 MiB；核心镜像只存
非零页（约 10.4 MiB），最多再保留一份宏包/上下文检查点。字体缓存最多 16 项；文件记录最多 4096 条，输出缓冲合计最多 8 MiB，转曲标签最多 20,000 字符。
缩短测试空闲时限后确认 Worker 已结束，随后请求确实新建 Worker；正式默认仍为 60 秒。

编辑器另外合并约 80 ms 的输入。表中渲染耗时不包含该等待、IPC 绘制和用户界面刷新。
首次下载不计入测量；首次初始化和复杂图形仍会更慢。未宣称任意图形都能在固定时限完成。

正确性验证直接比较实际生成的 SVG。原抛物线、箭头/希腊字母节点和文字标签与旧 Worker
输出逐字节一致；原图仍为 280×126 px。原生声明测试以显式展开后的图形为参照，覆盖
定义顺序、定界参数、局部/全局作用域、重定义、分支、图形之间隔离、数学分隔符内前置
定义及 pgfplots 中的函数宏。另验证错误恢复、超时恢复和空闲重启。

复现：先运行 `npm run build && npm run validate:tikz` 准备经过校验的组件，再运行
`npm run benchmark:tikz`。可用 `node scripts/benchmark-tikz.mjs <worker.js> <report.json>`
指定旧安装包解出的 Worker；中间产物留在被忽略的 `.tmp-tikz-smoke/` 目录。
